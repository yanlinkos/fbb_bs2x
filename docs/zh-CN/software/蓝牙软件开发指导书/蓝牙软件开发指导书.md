# Preface<a name="ZH-CN_TOPIC_0000001713103213"></a>

**Overview<a name="section669mcpsimp"></a>**

BS2XV100 provides developers with interfaces for accessing and using BLE (Bluetooth Low Energy) through APIs (Application Programming Interfaces), including GAP advertising, connection, and GATT service registration and service discovery. Interfaces for other protocols will be released incrementally.

# Overview<a name="ZH-CN_TOPIC_0000001713023229"></a>

BS2XV100 provides developers with development and application interfaces for BLE functionality through APIs (Application Programming Interfaces), including GAP, GATT server, and GATT client interfaces.

The function descriptions of each component are as follows:

-   GAP: Generic Access Profile, includes BLE local settings and BLE discovery and connection interfaces.
-   GATT: Generic Attribute Profile, includes service registration, service discovery, and other related interfaces.

>![](public_sys-resources/icon-note.gif) **Note:** 
>This document describes the basic processes and API interface descriptions of each module function.

# GAP Interface<a name="ZH-CN_TOPIC_0000001664983686"></a>





## Overview<a name="ZH-CN_TOPIC_0000001665143402"></a>

GAP implements functions such as BLE device on/off control, device information management, advertising management, active connection and disconnection, etc.

## Development Flow<a name="ZH-CN_TOPIC_0000001713023225"></a>

**Usage Scenarios<a name="section775mcpsimp"></a>**

Turning on the BLE device is the prerequisite for using BLE functionality. After BLE is started, device information management can be performed, including obtaining and setting the local device name, obtaining the local device address, obtaining pairing information, and obtaining the remote device name/device type/received signal strength, etc.

When a BLE device needs to passively establish a connection with a peer device, advertising parameters can be set and advertising started to wait for the peer connection. When a BLE device needs to actively establish a connection with a peer device, it can initiate an active connection to the peer. When the peer address is known, the user can directly initiate an active connection to the peer. When the peer address is unknown, the scanning function of the BLE device can be enabled to obtain information about advertising devices and initiate an active connection to the peer. When the BLE device is in a connected state, device connection information can be obtained. When the BLE device no longer needs to maintain a connection with the peer device, it can actively disconnect.

**Development Flow<a name="section904mcpsimp"></a>**

For specific programming examples of GAP development, refer to application/samples/bt.

Typical flow for GAP development:

Slave：

1.  Call gap_ble_register_callbacks to register user callback functions.
2.  Call enable_ble to turn on the Bluetooth switch.
3.  Call gap_ble_set_local_addr to set the local Bluetooth address.
4.  Call gap_ble_set_local_name to set the local device name.
5.  Call gap_ble_set_adv_param to set advertising parameters
6.  Call gap_ble_set_adv_data to set advertising data
7.  Call gap_ble_start_adv to start advertising.

Master：

1.  Call gap_ble_register_callbacks to register user callback functions.
2.  Call enable_ble to turn on the Bluetooth switch.
3.  Call gap_ble_set_local_addr to set the local Bluetooth address.
4.  Call gap_ble_set_local_name to set the local device name.
5.  Call gap_ble_set_scan_parameters to set scan parameters
6.  Call gap_ble_start_scan to start scanning
7.  Call gap_connect_remote_device to connect to the target device.
8.  Call gap_ble_pair_remote_device to pair with the target device

Setting passkey:

1.  Call gap_ble_set_local_passkey to set the passkey value
2.  Call **gap_ble_set_sec_param** to set security parameters
3.  Call gap_ble_passkey_entry to input the passkey

User-specified NV pairing information storage:

1.  Obtain pairing information based on auth_complete_cb callback
2.  Call **ble_set_nv_pair_keys** to store pairing information to NV with specified index

**Development Flow<a name="section161008381712"></a>**

The typical development flow for BLE Passkey authentication is as follows:

1.  **gap_ble_set_sec_param** sets security parameters. Both device ends will select the corresponding authentication method based on the security parameters.
2.  The connecting end calls gap_connect_remote_device to initiate the connection and ensures the connection is completed.
3.  After the connection is completed, call the pairing initiation interface: gap_ble_pair_remote_device. This interface can be called on both G and T nodes.
4.  If the device is configured as a display device (IO capability: display only or display with Yes/No selection), the device will only receive the passkey_notify_cb callback. At this point, the device needs to display the data. The passkey is generated by the protocol stack as a random 6-digit number on the current device.
5.  If the device is configured as an input device (IO capability: keyboard only or keyboard and display), the device will only receive the passkey_req_cb callback. At this point, the device requires the user to input the passkey displayed by the peer device.
6.  After the input device successfully calls the gap_ble_passkey_entry input interface, wait for the pairing to complete.

Notes:

1、When calling gap_ble_pair_remote_device, during the encryption pairing process, do not perform other services (especially the “service discovery” service), as this may cause pairing to fail.

2、Setting connection parameters (connection interval, latency period) too large will result in excessively long pairing time.

## Notes<a name="ZH-CN_TOPIC_0000001664983690"></a>

-   When this product operates only as a BLE device, it supports up to eight BLE connections. When operating as both a BLE device and a StarLight device simultaneously, it supports a total of eight connections.
-   If the device cannot be scanned, first check whether the device is already in the paired device list, or whether the device has been paired with another device (in this case, the device-side pairing information needs to be cleared first).
-   If encryption of pairing keys in NV storage is required, the macro CONFIG_NV_SUPPORT_ENCRYPT needs to be enabled. In the configuration interface, go to Middleware->Utils-> and check nv_support encrypt. Set the storage mode of pairing keys in NV to encrypted storage before enabling the protocol. This setting takes effect for both Bluetooth and StarLight simultaneously.

**Development Flow<a name="section904mcpsimp"></a>**

For specific programming examples of GATT server development, refer to application/samples/bt.

Typical flow for GATT server development: add services, characteristics, and descriptor information, and start the service.

1.  Call gatts_register_callbacks to register GATT server user callback functions.
2.  Call enable_ble to turn on the Bluetooth switch.
3.  Call gatts_register_server to create a server.
4.  Call gatts_add_service to create a service based on UUID.
5.  Call gatts_add_characteristic to add characteristic values to the created service.
6.  Call gatts_add_descriptor to add descriptor information to the characteristics in the service.
7.  Call gatts_start_service to start the service.
8.  Start advertising and wait for the peer connection.
9.  After being enabled as “notifiable” by the peer, call gatts_notify_indicate or gatts_notify_indicate_by_uuid to send characteristic value notifications to the peer.

# GATT Client Interface<a name="ZH-CN_TOPIC_0000001665143398"></a>



## Overview<a name="ZH-CN_TOPIC_0000001713103217"></a>

GATT is a general specification for sending and receiving data based on BLE GAP connections, supporting data transmission between two BLE devices.

## Development Flow<a name="ZH-CN_TOPIC_0000001664983682"></a>

**Usage Scenarios<a name="section775mcpsimp"></a>**

**Development Flow<a name="section904mcpsimp"></a>**

For specific programming examples of GATT client development, refer to application/samples/bt.

Typical flow for GATT client development: connect to the peer device, discover the peer device’s services, read/write peer characteristic values, and subscribe to peer notifications or indications.

1.  Call gattc_register_callbacks to register GATT client user callback functions.
2.  Call enable_ble to turn on the Bluetooth switch.
3.  Call gattc_register_client to create a client.
4.  Recursively call gattc_discovery_service, gattc_discovery_character, and gattc_discovery_descriptor to obtain the peer’s attribute database.
5.  Call gattc_write_req or gattc_write_cmd to write the client characteristic configuration of the concerned peer characteristic to 0x0001 or 0x0002. When set to the former, characteristic notifications of the concerned characteristic can be received. When set to the latter, characteristic indications of the concerned characteristic can be received.
6.  Call the corresponding read/write interfaces to operate on the GATT server’s characteristics and descriptors.
