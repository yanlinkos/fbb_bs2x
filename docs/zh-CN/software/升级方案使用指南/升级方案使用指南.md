# Overview<a name="ZH-CN_TOPIC_0000001802979890"></a>



## Function Description<a name="ZH-CN_TOPIC_0000001805091786"></a>

The firmware upgrade function can be used to update the firmware of the chip on a single board.

The BS2X firmware includes the partition table, secondary bootloader (Flashboot), user firmware image (Application), and NV image. It supports upgrading the secondary bootloader and user firmware image. Currently, the upgrade modes include full image upgrade and compressed upgrade.

-   Full image upgrade: The new firmware image is packaged into the firmware upgrade package (hereinafter referred to as the "upgrade package") without processing, and is directly updated to the target location on the single board.
-   Compressed upgrade: The new firmware image is compressed and packaged into the upgrade package. It is decompressed and restored on the device first, and then updated to the target location.

## Firmware Upgrade Flow<a name="ZH-CN_TOPIC_0000001805252022"></a>

From an end-to-end perspective, the entire chip firmware upgrade operation includes the following processes, as shown in [Figure 1](#fig16865101514911).

-   Upgrade package creation: After the firmware development is complete, the process of packaging the firmware images to be upgraded into a firmware upgrade package file based on the actual situation.
-   Upgrade package transmission: Transmitting the upgrade package to the single board. Depending on the actual situation, there may be multiple transmission methods, such as BLE, NearLink, UART, USB, and so on.
-   Upgrade package storage: Saving the firmware upgrade package transmitted to the single board to the local storage. In BS2X, the firmware upgrade package is stored in Flash.
-   Local verification of the upgrade package: Before the upgrade program is replaced, the integrity and validity of the upgrade package are verified on the single board.
-   Local upgrade using the upgrade package: Updating the new firmware to the target location on the single board. In BS2X, the Flashboot program is responsible for upgrading the Flashboot itself and the APP image.

# Upgrade Package Creation<a name="ZH-CN_TOPIC_0000001851901485"></a>




## Flow Principle<a name="ZH-CN_TOPIC_0000001805112244"></a>

**Figure 1**  Upgrade Package Creation Flow<a name="fig47601738135110"></a>  
![](figures/升级包制作流程.png "Upgrade Package Creation Flow")

The upgrade package creation flow is shown in [Figure 1](#fig47601738135110). The specific operation steps are as follows:

1.  <a name="li8171529465"></a>Compile and generate a signed plaintext new image.
2.  <a name="li205945352468"></a>Process the new image. The processing methods include the following scenarios:
    -   Compress the new image to generate a compressed new image.
    -   Leave the new image unprocessed.

3.  <a name="li25431424820"></a>Add an upgrade image header to the image generated in [Step 2](#li205945352468).
4.  Perform [Step 1](#li8171529465) to [Step 3](#li25431424820) on all images to be upgraded according to the selected processing methods.
5.  <a name="li783094165412"></a>Merge all generated upgrade image files with upgrade image headers into the final upgrade package, add an upgrade package header to the entire package, and perform digital signature.

>![](public_sys-resources/icon-note.gif) **Note:** 
>BS2X does not support secure upgrade. No digital signature is added in [Step 5](#li783094165412).

## Development Flow<a name="ZH-CN_TOPIC_0000001805272080"></a>

After all images are compiled, the upgrade package can be created by executing "build/config/target\_config/bs21/build\_bs21\_update.py". In the "build\_bs21\_update.py" file, configure the paths of each image and other parameters required by the scripts, and invoke the upgrade package creation script "build/script/build\_upg\_pkg.py". The paths configured in "build\_bs21\_update.py" can be modified according to the actual paths. The scripts and configuration files are described as follows:

-   When BS2X compiles and generates a new firmware, it automatically packages the generated firmware into an upgrade package. Users only need to select the firmware to be upgraded. Configure the file path of the firmware to be upgraded: build/config/target\_config/bs21/config.py. As shown in [Figure 1](#fig77657269522), select the firmware to be upgraded in the upg\_pkg option. The supported firmware for upgrade includes: flashboot and application.

    **Figure 1**  Adding an Upgrade Image to the Upgrade Package<a name="fig77657269522"></a>  
    ![](figures/升级包添加升级镜像.png "Adding an Upgrade Image to the Upgrade Package")

-   Upgrade package path: output/bs21/acore/bs21-sle-ble-central-peripheral/fota.fwpkg.
-   The upgrade package creation script is build/script/build\_upg\_pkg.py. The parameter descriptions of the upgrade package creation script are shown in [Table 1](#table2035291410209).
-   The configuration file is build/config/target\_config/bs21/fota/1M\_flash/fota.cfg (for the external flash version, build/config/target\_config/bs21/fota/extern\_flash/fota.cfg). The fields in the configuration file are described in [Table 2](#table4436131111208).
-   The upgrade image mode can be configured in the configuration file "fota.cfg". As shown by the upgrade image mode flag DecompressFlag in [Table 2](#table4436131111208), two upgrade modes are supported: compressed and full.
-   When generating the fota package, a version feature code is inserted based on the chip type and the feature code configured by the user. A consistency check is performed during the upgrade. The feature macro configuration is shown in the following figure. If the consistency check fails, the upgrade stops and the currently stored upgrade package is deleted.

# Upgrade Package Transmission<a name="ZH-CN_TOPIC_0000001805270688"></a>

The transmission of the upgrade package is implemented by the application program and can use multiple methods, including Bluetooth, NearLink, USB, and UART. The following describes the basic flow of each transmission method and the usage of related tools.

The BLE end-to-end upgrade interaction flow of BS2X is shown in [Figure 1](#fig209801945145517). To enable BLE OTA upgrade on the Server side, the BLE OTA channel needs to be registered first, as shown in [Figure 2](#fig5764163615120), and then the BLE OTA service needs to be registered, as shown in [Figure 3](#fig165212612217). You can refer to the BLE UART Sample, with the code path application/samples/products/ble\_uart.

### Upgrading the Production Test Firmware to the Commercial Firmware<a name="ZH-CN_TOPIC_0000001852071177"></a>

After the production test is completed, the operation of writing the upgrade flag needs to be performed, and the local upgrade flow needs to be entered. The upgrade flag area is located in the last 4 KB space of the upgrade package area, with the format as follows. For the structure of the upgrade flag, see middleware/utils/update/inner\_include/upg\_definitions.h.

```
typedef struct fota_upgrade_flag_area {
    uint32_t head_magic;
    uint32_t head_before_offset;
    uint32_t package_length;
    uint32_t firmware_num;
    uint8_t  firmware_flag[UPG_FIRMWARE_MAX_NUM][UPG_FLAG_RETYR_TIMES];
    uint8_t  nv_flag[UPG_FLAG_RETYR_TIMES];
    uint8_t  ver_change_flag;
    uint32_t update_result;
    uint32_t nv_data_offset;
    uint32_t nv_data_len;
    uint32_t nv_hash_offset;
    uint32_t nv_hash_len;
    uint32_t complete_flag;
    uint32_t head_end_magic;
} fota_upgrade_flag_area_t;
```

The following is a code example for writing the enable flag, for reference:

```
    fota_upgrade_flag_area_t fota_flag;
    memset_s((uint8_t *)&fota_flag, sizeof(fota_upgrade_flag_area_t), 0xff, sizeof(fota_upgrade_flag_area_t));
    fota_flag.head_magic = 0x55aa55aa;
    fota_flag.head_before_offset = 0;
    fota_flag.package_length = fota_len;  // Upgrade package size
    fota_flag.firmware_num = fw_num;  // Number of firmware images in the upgrade package
    fota_flag.head_end_magic = 0xaa55aa55;
    partition_information_t info;
    uapi_partition_init();
    errcode_t ret_val = uapi_partition_get_info(PARTITION_FOTA_DATA, &info);
    uint32_t flag_address = info.part_info.addr_info.addr + info.part_info.addr_info.size - 0x1000;
    uint32_t status = (uint32_t)osal_irq_lock();
    uapi_sfc_reg_erase(flag_address, 0x1000);
    uapi_sfc_reg_write(flag_address, (uint8_t *)&fota_flag, sizeof(fota_upgrade_flag_area_t));
    // uapi_flash_block_erase(0, flag_address, 0x1000);    // External flash version
    // uapi_flash_write_data(0, flag_address, (uint8_t *)&fota_flag, sizeof(fota_upgrade_flag_area_t));    // External flash version
    osal_irq_restore(status);
    upg_reboot();  // Reset the single board
```

>![](public_sys-resources/icon-note.gif) **Note:** 
>In the preceding code, users need to adjust the variables fota\_len and fw\_num. fota\_len is the upgrade package size, and fw\_num is the number of firmware images in the upgrade package. For example, if the upgrade package contains only Application.bin, then fw\_num = 1.

## HID Upgrade<a name="ZH-CN_TOPIC_0000002096253060"></a>

Taking BS26 as an example, the SDK provides three flashboot images:

-   flashboot-bs26-n1200: Supports OTA upgrade. That is, after the OTA upgrade is complete, the FOTA area data is decompressed and copied to the APP main area.
-   flashboot-bs26-n1200-usb: Supports USB HID upgrade, but does not support the copy after OTA upgrade.
-   flashboot-bs26-n1200-usb-with-ota: Supports USB HID upgrade and the copy after OTA upgrade.

Therefore, if the flashboot needs to have the HID upgrade function, flashboot-bs26-n1200-usb or flashboot-bs26-n1200-usb-with-ota should be used. That is, configure 'flashboot\_cfg' to the required flashboot in the corresponding config.py.

The flashboot image with the USB HID upgrade function is larger, so attention is required when dividing partitions.

USB HID upgrade requires an additional 4 KB partition to be used as the upgrade flag determination, that is, the fota data with the partition ID of 0x26. Different from other OTA upgrade methods, HID upgrade only needs the last 4K of the fota data to store the upgrade flag information, while other OTA upgrade methods need to store the upgrade image in the fota area.

In addition, USB HID upgrade requires an additional ID 0x29 in the partition table to store the vid, pid, and io detection information.

## Host-Controlled HID Upgrade<a name="ZH-CN_TOPIC_0000002174742721"></a>

HID upgrade initializes USB at power-on (plugging in/removing the USB) and waits for burntool to send the USB upgrade command, so the power-on time is increased. To reduce the power-on time, a flashboot version for host-controlled HID upgrade is added. Taking BS26 as an example:

flashboot-bs21e-1100e-usb-with-control and flashboot-bs21e-1100e-usb-with-ota-with-control.

When packaging the fwpkg, select the flashboot version with '-with-control'. By default, HID upgrade is not performed at power-on. The host needs to send commands to control bs2x to write the HID upgrade flag register and the software reset register. After the software reset, HID upgrade is performed.

1.  HID upgrade flag register: Write 0x5A to 0x5702C010.
2.  Software reset register: Write 0 to 0x57004600.

# Local Upgrade Using the Upgrade Package<a name="ZH-CN_TOPIC_0000001805091538"></a>

In BS2X, the local upgrade program mainly runs in the Flashboot program. The upgradeable images are Flashboot and Application.

When the Flashboot program upgrades the Flashboot itself, it copies the Flashboot to the Flashboot backup area to avoid abnormal power-off. After all images are updated, the single board automatically resets, and the Application image is entered after the reset.

**Question 6: How to upgrade the partition table<a name="section17608334185212"></a>**

To upgrade from an old partition table to a new one, two upgrades are required for a complete update.

>![](public_sys-resources/icon-notice.gif) **Notice:** 
>1.  The partition table upgrade flow carries the risk of bricking the device. Users should operate with caution and ensure that power is not lost during the upgrade.
>2.  Both the BS2X startup and upgrade flows depend on the partition table. In principle, the partition table should not be upgraded. The partition table must be fixed before product production and should not be modified afterwards. The above method of upgrading the partition table is not recommended for the mass production phase.

The specific steps are as follows:

1.  Add the following modifications based on the old version and compile an intermediate version.
2.  Before the Application initializes the partition table, modify the information in the partition table upgrade area of the old version to make it consistent with the new version. The code modification is shown in [Figure 6](#fig12844144505817).

    **Figure 6**  Modifying the Partition Table Upgrade Area Information before Initializing the Partition Table<a name="fig12844144505817"></a>  
    ![](figures/初始化分区表之前修改分区表升级区信息.png "Modifying the Partition Table Upgrade Area Information before Initializing the Partition Table")

    ![](figures/zh-cn_image_0000001990030097.png)

    Code example:

    ```
    static uint32_t g_partition[0x400] = {
        // Partition table image header, no modification required
        0x4b87a52d, 0x00010000, 0x00000000, 0x000c001c,
        0x26252301, 0x30292827, 0x00333231,
        // 0x00
        0x00001000, 0x00008000,
        // 0x01
        0x00009000, 0x00008000,
        // 0x23
        0x00011000, 0x0008c000,
        // 0x25
        0x000FE000, 0x00002000,
        // 0x26
        0x0009d000, 0x00061000,
        // 0x27
        0x00000000, 0x00000000,
    };
    errcode_t ret = osal_irq_lock();
    uapi_sfc_reg_erase(0x0, 0x1000);
    uapi_sfc_reg_write(0x0, (uint8_t *)g_partition, 0x400);
    osal_irq_restore(ret);
    ```

3.  After the upgrade transmission flow ends and before the single board resets, modify other areas of the old version partition table so that the partition table remains consistent with the new version partition table. The code modification for the DFU upgrade is shown in [Figure 7](#fig114581012115813), and the code modification for the OTA upgrade is shown in [Figure 8](#fig1350478132410).

    **Figure 7**  Updating the Partition Table after the DFU Upgrade Transmission Flow Ends<a name="fig114581012115813"></a>  
    ![](figures/DFU升级传输流程结束后更新分区表.png "Updating the Partition Table after the DFU Upgrade Transmission Flow Ends")

    **Figure 8**  Updating the Partition Table after the OTA Upgrade Transmission Flow Ends<a name="fig1350478132410"></a>  
    ![](figures/OTA升级传输流程结束后更新分区表.png "Updating the Partition Table after the OTA Upgrade Transmission Flow Ends")

4.  Based on the above modifications, compile the intermediate version. Upgrade the old version to this intermediate version to complete the update of the partition table upgrade area. Then upgrade to the new version firmware (including the new Flashboot and App images) to complete the partition table update.
