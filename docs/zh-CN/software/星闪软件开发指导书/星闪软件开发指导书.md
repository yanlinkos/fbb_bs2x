# Overview<a name="ZH-CN_TOPIC_0000001664983290"></a>

BS2XV100 provides developers with SLE feature development and application interfaces through the API (Application Programming Interface), including Device Discovery, Connection Manager, SSAP, etc.

The functions of each component are described as follows:

-   Device Discovery: NearLink device discovery protocol, including device management, device advertisement, and device discovery interfaces.
-   Connection Manager: NearLink connection management protocol, including device connection and pairing related interfaces.
-   SSAP: SparkLink Service Access Protocol, including interfaces for service registration, service discovery, attribute data read/write, and other functions.
-   Low Latency: Low-latency initialization and low-latency data transmission and reception interfaces.

>![](public_sys-resources/icon-note.gif) **Note:** 
>This document describes the basic flow of each module function and the API interface descriptions.

## Overview<a name="ZH-CN_TOPIC_0000001713102833"></a>

-   When an SLE device needs to perform device discovery, you can first set the device discovery parameters, then enable device discovery, and observe the discovered device advertisement packets through the callback function.

**Development Flow<a name="section904mcpsimp"></a>**

The typical development flow of Device Discovery is as follows. For specific programming examples, refer to application/samples/bt.

**Terminal Node：**

1.  Call enable\_sle to turn on the SLE switch.
2.  Call sle\_announce\_seek\_register\_callbacks to Register the device advertisement and device discovery callback functions.
3.  Call sle\_set\_local\_addr to Set the local device address.
4.  Call sle\_set\_local\_name to Set the local device name.
5.  Call sle\_set\_announce\_param to Set the device advertisement parameters.
6.  Call sle\_set\_announce\_data to Set the device advertisement data.
7.  Call sle\_start\_announce to start device advertisement.

**Grant Node：**

1.  Call enable\_sle to turn on the SLE switch.
2.  Call sle\_announce\_seek\_register\_callbacks to Register the device advertisement and device discovery callback functions.
3.  Call sle\_set\_local\_addr to Set the local device address.
4.  Call sle\_set\_local\_name to Set the local device name.
5.  Call sle\_set\_seek\_param to Set the device discovery parameters.
6.  Call sle\_start\_seek to start device discovery, and obtain the information of devices currently performing device advertisement in the callback function.

## Precautions<a name="ZH-CN_TOPIC_0000001665143026"></a>

-   When the BS2XV100 product works only as an SLE device, it supports up to eight connections. When it works as both a BLE and an SLE device, it supports eight connections in total.
-   If no device is scanned, check whether the device is already in the paired device list, or whether the device has already been paired with other devices (in this case, the pairing information on the device side needs to be cleared first).

# Connection Manager Interface<a name="ZH-CN_TOPIC_0000001713022853"></a>



## Overview<a name="ZH-CN_TOPIC_0000001713022857"></a>

The Connection Manager interface is the software implementation of the NearLink connection management protocol. Its main functions include connection, pairing, and reading the RSSI value of the remote device.

## Development Flow<a name="ZH-CN_TOPIC_0000001664983294"></a>

**Usage Scenario<a name="section775mcpsimp"></a>**

When a device needs to establish a connection with the peer device, it can initiate a connection request to the peer device. During the connection process, the device can read the RSSI value of the remote device. When the device needs to update the connection parameters, it can initiate a connection parameter update request to the peer device. When the device needs to pair with the peer device, it can initiate a pairing request to the peer device. During the pairing process, the pairing status between the current local device and the specified peer device can be obtained. The device can obtain the current number of paired devices, the current linked list of paired device information, and the current link role.

**Development Flow<a name="section904mcpsimp"></a>**

The typical development flow of the Connection Manager is as follows. For specific programming examples, refer to application/samples/bt.

**Terminal Node：**

1.  Call enable\_sle to turn on the SLE switch.
2.  Call sle\_announce\_seek\_register\_callbacks to register the device advertisement and device discovery callback functions.
3.  Call sle\_connection\_register\_callbacks to register the connection management callback function.
4.  Call sle\_set\_local\_addr to set the local device address.
5.  Call sle\_set\_local\_name to set the local device name.
6.  Call sle\_set\_announce\_param to set the device advertisement parameters.
7.  Call sle\_set\_announce\_data to set the device advertisement data.
8.  Call sle\_start\_announce to start device advertisement.

**Grant Node：**

1.  Call enable\_sle to turn on the SLE switch.
2.  Call sle\_announce\_seek\_register\_callbacks to register the device advertisement and device discovery callback functions.
3.  Call sle\_connection\_register\_callbacks to register the connection management callback function.
4.  Call sle\_set\_local\_addr to set the local device address.
5.  Call sle\_set\_local\_name to set the local device name.
6.  Call sle\_set\_seek\_param to set the device discovery parameters.
7.  Call sle\_start\_seek to start device discovery, and obtain the device information of the device being advertised in the callback function.
8.  Call sle\_connect\_remote\_device to initiate a connection request to the peer device.
9.  Call sle\_pair\_remote\_device to initiate a pairing request to the peer device.
10. Call sle\_get\_paired\_devices\_num to obtain the current number of paired devices.
11. Call sle\_get\_paired\_devices to obtain the current paired device information.
12. Call sle\_get\_pair\_state to obtain the pairing state.
13. Call sle\_get\_connect\_role to obtain the link role.

**Development Flow<a name="section904mcpsimp"></a>**

The typical development flow of the SSAP server is as follows: register the SSAP server, register the local property database, receive requests and commands from the peer device, and send notifications and indications to the peer device. For specific programming examples, refer to application/samples/bt.

1.  Call enable\_sle to turn on the SLE switch.
2.  Call ssaps\_register\_callbacks to register SSAP server callbacks.
3.  Call sle\_announce\_seek\_register\_callbacks to register the device advertisement and device discovery callback functions.
4.  Call ssaps\_register\_server to create a server entity.
5.  Call ssaps\_add\_service\_sync, ssaps\_add\_property\_sync, ssaps\_add\_descriptor\_sync, and ssaps\_start\_service to register the local property database. After each service and its content are added, call ssaps\_start\_service to start the service.
6.  Call sle\_set\_local\_addr to set the local device address.
7.  Call sle\_set\_local\_name to set the local device name.
8.  Call sle\_set\_announce\_param to set the device advertisement parameters.
9.  Call sle\_set\_announce\_data to set the device advertisement data.
10. Call sle\_start\_announce to start device advertisement.
11. The connection is established.
12. Receive read/write requests from the peer device. When the peer device reads or writes a property or descriptor that requires authorization, call ssaps\_send\_response to send a response to the peer device and modify the local property value.
13. When the client feature configuration descriptor of a property is 0x0001, call ssaps\_notify\_indicate to send a notification to the peer device when the property value changes. When the client feature configuration descriptor of a property is 0x0002, call ssaps\_notify\_indicate to send an indication to the peer device when the property value changes.

**Development Flow<a name="section904mcpsimp"></a>**

The typical development flow of the SSAP Client is as follows: register the SSAP Client, find the peer property database, send requests and commands to the peer device, and receive notifications and indications from the peer device. For specific programming examples, refer to application/samples/bt.

**SSAP Server：**

1.  Call enable\_sle to turn on the SLE switch.
2.  Call ssaps\_register\_callbacks to register SSAP server callbacks.
3.  Call sle\_announce\_seek\_register\_callbacks to register the device advertisement and device discovery callback functions.
4.  Call ssaps\_register\_server to create a server entity.
5.  Call ssaps\_add\_service\_sync, ssaps\_add\_property\_sync, ssaps\_add\_descriptor\_sync, and ssaps\_start\_service to register the local property database. After each service and its content are added, call ssaps\_start\_service to start the service.
6.  Call sle\_set\_local\_addr to set the local device address.
7.  Call sle\_set\_local\_name to set the local device name.
8.  Call sle\_set\_announce\_param to set the device advertisement parameters.
9.  Call sle\_set\_announce\_data to set the device advertisement data.
10. Call sle\_start\_announce to start device advertisement.
11. The connection is established.
12. Receive read/write requests from the peer device. When the peer device reads or writes a property or descriptor that requires authorization, call ssaps\_send\_response to send a response to the peer device and modify the local property value.
13. When the client feature configuration descriptor of a property is 0x0001, send a notification to the peer device when the property value changes. When the client feature configuration descriptor of a property is 0x0002, send an indication to the peer device when the property value changes.

**SSAP Client：**

1.  Call enable\_sle to turn on the SLE switch.
2.  Call ssapc\_register\_callbacks to register SSAP client callbacks.
3.  Call sle\_announce\_seek\_register\_callbacks to register the device advertisement and device discovery callback functions.
4.  Call ssapc\_register\_client to create a client entity.
5.  Call ssapc\_find\_structure recursively to find the peer property database.
6.  If you are interested in a property of the peer device, you can call ssapc\_write\_req or ssapc\_write\_cmd to write the client feature configuration descriptor of the property as 0x0001 or 0x0002. The former enables the peer device's property notification, and the latter enables the peer device's property indication.
7.  Call the read interface ssapc\_read\_req and the write interface ssapc\_write\_req to operate the peer property database.

**Development Flow<a name="section161008381712"></a>**

The typical development flow of SLE Passkey authentication is as follows:

1.  After the SLE protocol stack is initialized, the two interconnected devices must call the security parameter setting interface to configure the IO capabilities of both devices and the man-in-the-middle attack defense flag.

    When the pairing decision uses Passkey authentication, set the man-in-the-middle attack defense flag to: SLE\_PAIRING\_DEFEND\_MITM, and set the IO capabilities of both devices according to Table SLE Authentication Method Decision Description.

2.  The connection end initiates a connection and ensures that the connection is completed.
3.  After the connection is completed, call the pairing initiation interface: sle\_pair\_remote\_device. This interface can be called on both G and T nodes.
4.  Configure the device as a display device through the security parameter setting interface (IO capability: Display only or Display and can choose Yes or No). Then the device will only receive the passkey\_notify\_cb callback. At this time, the device needs to display the data, and the passkey is a random 6-digit number generated by the protocol stack on the current device.
5.  Configure the device as an input device through the security parameter setting interface (IO capability: Keyboard only or Support keyboard and display). Then the device will only receive the passkey\_req\_cb callback. At this time, the device requires the user to enter the passkey displayed on the peer device.
6.  After the input device successfully calls the passkey input interface, wait for the pairing to complete, which typically takes 2s\~4s.

# SLE Channel Map Interface<a name="ZH-CN_TOPIC_0000002523758039"></a>



## Overview<a name="ZH-CN_TOPIC_0000002523878553"></a>

SLE frequency hopping supports user-defined hopping channels.

## Development Flow<a name="ZH-CN_TOPIC_0000002491638816"></a>

**Usage Scenario<a name="section4346153310231"></a>**

The typical usage scenario of the SLE Channel Map interface is to avoid channels occupied by WiFi. For example, if WiFi is 20 MHz and uses channel 6, it is recommended to avoid channels 2427-2447.

As shown in the following figure, the WiFi 2.4 GHz band is divided into 14 overlapping, staggered 20 MHz channels, numbered from 1 to 14, and adjacent channels overlap with each other to a certain extent.

![](figures/zh-cn_image_0000002491652212.png)

To improve the wireless network rate of wireless terminals, the RF channel operating bandwidth can be increased. If two 20 MHz channels are bound together into a 40 MHz channel, one of them is the primary channel and the other is the secondary channel. If the center frequency of the primary channel is higher than that of the secondary channel, it is 40MHz-; otherwise, it is 40MHz+. In the 2.4 GHz band, the interval between two bound channels is 4 (for example, 1,5; 2,6).

**Development Flow<a name="section367123844713"></a>**

The typical development flow of the SLE Channel Map is as follows:

**Client:**

1.  When the connection is reported as successful, call sle\_channel\_map to set the channel preference.
