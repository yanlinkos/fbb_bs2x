## Platform Log Interface<a name="ZH-CN_TOPIC_0000001959517505"></a>

The specific UART BUS mapping is shown in [Table 1](#table16157211132719). To use the normal printing interface, include the soc\_osal.h header file and call the osal\_printk interface for formatted LOG output.

### DIAG Serial Printing<a name="ZH-CN_TOPIC_0000001932358334"></a>

The DIAG printing mode parses logs through the DebugKits tool. By default, UART\_BUS1 (UART handle name selected by software configuration parameters) (UART\_H0 (hardware PIN name)) is used to print DIAG logs. The HSO maintenance and testability function module provides the following functions:

-   Log printing. Users can print debugging information to the Message view of DebugKits through the log printing interface.
-   Command registration and processing. Users can register commands and command processing functions to enter commands in the command-line view of DebugKits to control board-side operations.
-   System maintenance and testability information collection. DIAG supports obtaining system statistics (such as memory usage and task information) to help users locate problems.

Taking the example of adding debugging logs in chips/bs2x/main\_init/app\_os\_init.c, the process is as follows:

1.  Before using DIAG logs, users need to confirm whether the file that calls the interface has been added to the module. >![](public_sys-resources/icon-note.gif) **Note:** 
>Note that DIAG logs support only parameters with a length of 32 bits or less, such as "%d", "%u", "%x", and "%p". They do not support parameters with a length greater than 32 bits, such as "%ld" and "%s", nor floating-point parameters, such as "%f".
>The normal printing mode outputs logs through the serial port directly at the interface call location. If there are too many logs, the current caller thread may be blocked, causing unexpected phenomena. The DIAG printing mode throws messages to the log thread through events for printing and does not block the printing caller, but it increases the codesize. It is recommended to use it when memory is sufficient, as it is more flexible than the normal mode. Choose the appropriate mode based on the actual scenario.

### APP Sleep Log<a name="ZH-CN_TOPIC_0000001932198950"></a>

By default, the App records the scheduling idle time through HSO logs at intervals. While printing sleep statistics, the watchdog is fed (if no printing occurs for a long time, the watchdog may time out, so the watchdog is fed), as shown in [Figure 1](#fig1901mcpsimp). ### APP Panic Log<a name="ZH-CN_TOPIC_0000001959437729"></a>

A kernel panic is an action taken by the operating system when it detects an internal fatal error and cannot safely handle the error. When the kernel encounters an exception, it runs the kernel\_panic function and prints all the information obtained when the exception occurs as much as possible.

-   Principle

    There are various causes of exceptions. Through the call information printed for the exception, find the reason for calling kernel\_panic. Common causes include kernel stack overflow, divide-by-zero exceptions in kernel space, out-of-bounds memory access, and kernel deadlocks.

-   Triggering method

    Read address 0 in kernel mode.

When a panic exception occurs on the APP core, the panic reason 0x2003 and the corresponding panic id are printed, as shown in [APP panic log](APP-panic日志.md). For the panic id, see [Table 1](PANIC-ID.md#table279mcpsimp).

# Log Analysis<a name="ZH-CN_TOPIC_0000001932198958"></a>

Common exception scenarios include watchdog timeout, hardfault, mem fault, bus fault, usage fault, panic exceptions, forced watchdog reset, and so on. When an exception occurs, the abnormal restart reason is printed and the system restarts. APP restart exceptions are represented by 0x2xxx, specifically 0x2000\~0x2010, 0x2040\~0x2044, 0x2080, and 0x2100.







## Obtaining Halt Information<a name="ZH-CN_TOPIC_0000001932358346"></a>




### Obtaining Maintenance and Testability Information from the Normal Printing Port<a name="ZH-CN_TOPIC_0000001959437741"></a>

-   When the hardware is connected to the serial port tool, if the board halts, the serial port tool can receive the halt information printed by the DFX process before reset. Users can locate the halt cause by analyzing the halt information. The halt LOG of the normal printing port is divided into four parts:
-   Halt scene: records the live values of RISCV general registers and some CSR registers when the halt occurs. For the description of each register, see [Viewing exception information](_异常信息查看.md#_异常信息查看) in the appendix.

    ![](figures/zh-cn_image_0000001932199022.png)

-   Thread stack information: records the stack top, stack size, and stack usage peak of the running thread stack when the halt occurs.

    ![](figures/zh-cn_image_0000001932358410.png)

-   Stack backtrace: traces the halt stack information. traceback 0 is the stack top position, sp addr and current sp are the current stack position, and sp content is the stack content.

    ![](figures/zh-cn_image_0000001959437805.png)

-   CPU Trace: records the PC and LR executed by the CPU over a period of time. step time stores the recording time. The larger the value, the closer the recorded time is to the halt scene.

>![](public_sys-resources/icon-note.gif) **Note:** 
    >Note: This is a data acquisition function. The recorded PC values may differ from the actual execution trace and may not correspond completely!

    ![](figures/zh-cn_image_0000001959517585.png)

    There are two ways to analyze the Trace:

    Method 1: Users can find the functions corresponding to the LR and PC addresses in the application.lst file generated during compilation to locate the halt execution scene.

    Method 2: Users can use the CFBB Tools provided by the IDE to parse the Trace. Open the tool and select the target used by the user.

    ![](figures/zh-cn_image_0000001932199026.png)

    Import the CPU Trace Information to the Trace information of CPU Trace end, click Parse to obtain the execution information of the past period, and locate the halt cause:

    ![](figures/zh-cn_image_0000001932358414.png)

### Obtaining Halt Dump Information<a name="ZH-CN_TOPIC_0000001959517521"></a>

The DebugKits tool provides a function to export the memory of the halt scene in binary format when a halt occurs, providing reference information to help developers locate and analyze halt issues. For detailed tool installation and usage, see "BS2XV100 DebugKits Tool User Guide". Only the Dump information export process is described here.

First, enter the tool page, click Options, and then select Change Chip. In the pop-up box, select BS2X to confirm the chip type. Refer to the figure to select the chip.

![](figures/zh-cn_image_0000001959437809.png)

Then click Connection and select Connect. In the pop-up window, select the connection mode and the corresponding channel number to connect. Refer to the figure to connect the chip.

![](figures/zh-cn_image_0000001959517589.png)

If it is the first time to connect the chip or the chip has a new version of the program, you need to update the HDB and reconnect before the log printing can be displayed correctly. Under the Option menu, select Update HDB, select the generated database directory (\\output\\bs2x\\database\_evb), and click OK to complete the configuration. For details, see the following figure: Configuring the database.

![](figures/zh-cn_image_0000001932199030.png)

Through the DebugKits tool, you can observe the specific information printed by the chip during runtime in real time. Refer to Figure DebugKits log printing. When a halt occurs, the Message view prints the last word and last dump information.

![](figures/zh-cn_image_0000001932358418.png)

The last word information sends the PC address, return address, stack address, and CPU register information when a halt occurs. Users can analyze the error type and locate the error cause based on the specific last word information. For details, see the following figure: last word information.

![](figures/zh-cn_image_0000001959437813.png)

The last dump information packages part of the information in memory into a bin file and stores it in the DumpInfo subdirectory of the DebugKits installation directory. For details, see the following figure: last dump generated file.

![](figures/zh-cn_image_0000001959517593.png)

>![](public_sys-resources/icon-note.gif) **Note:** 
>Note: Dumping memory to DebugKits takes some time (1–2 min). Therefore, if you need to use last dump to analyze halt information, do not reset immediately after a halt fault occurs; otherwise, the last dump information may not be completely obtained.

### Exporting by Connecting to the J-Link Debugger<a name="ZH-CN_TOPIC_0000001932198962"></a>

In scenarios where connecting a JTAG debugger is allowed, users can connect tools such as the J-Link emulator to further obtain information related to the halt scene. The following mainly describes the process of obtaining halt-related information through the J-Link emulator.

This section mainly describes the process of using the J-Link debugger at the halt scene to export halt information.

To debug with the J-Link emulator, first connect the chip SWD pins. The specific location is subject to the actual product. After the hardware is connected, run the Commandline\_bs2x\_mcpu.bat script in the toolkit (sdk\\tools\\bin\\jlink\_tool\\bs2x). ## Forced Watchdog Reset<a name="ZH-CN_TOPIC_0000001932358366"></a>

When a forced watchdog reset occurs, the system does not proactively trigger a hardfault or NMI exception. After waiting for the watchdog inside the chip to time out, the chip proactively triggers a reset. After the chip resets, it detects the reset cause 0x200d, triggers a panic exception, exports the last CPU trace, and triggers a restart. After the system restarts, it prints the panic restart: restart cause 0x2003, panic id 0x24, as shown in [Figure 1](#fig1156mcpsimp).

# Problem Locating<a name="ZH-CN_TOPIC_0000001959437761"></a>









## Peripheral Problem Locating Method<a name="ZH-CN_TOPIC_0000001959517541"></a>

Most peripheral exceptions are caused by incomplete initialization.

Peripheral initialization mainly consists of the following steps:

1.  Power on and enable the clock.
2.  Configure the pin mode.
3.  Register the HAL-layer callback functions.
4.  Register callbacks.
5.  Initialize the register configurations.

Troubleshooting ideas:

-   First check whether the clock/power supply is enabled. By default, the clocks of most drivers are disabled. Before use, check whether the CONFIG\_XXX\_SUPPORT\_LPC macro is enabled in the XXX driver initialization code. If it is not enabled, accessing the registers related to the XXX driver immediately causes a hang.
-   Check the return value of uapi\_xxx\_init to confirm whether the initialization is complete.
-   Check the software process (see the "BS2XV100 Device Driver Development Guide").
-   Check the hardware: whether the power-on is normal, whether the peripheral current is normal, and whether the same software burned into different hardware produces consistent results.
-   For other peripheral problems, refer to the peripheral description.

If the chip power consumption does not meet the requirement in the sleep state, the user needs to troubleshoot IO leakage as follows:

1.  For IO pins on the board-level circuit:
    -   If a pull-up resistor is externally connected to the pin, the pin needs to be configured as floating.
    -   If a pull-down resistor is externally connected to the pin, the pin can be configured as pull-down.
    -   In other cases, configure the pin as pull-down.

2.  For pins connected to external devices:

## Memory Maintenance and Testability Function<a name="ZH-CN_TOPIC_0000001932198986"></a>

Memory maintenance and testability is an important maintenance and testability method in any system. For example, you may want to know the current memory allocation and occupancy of the system, the stack occupancy of each task, and the specific memory allocation of a task. This memory information is crucial for memory optimization and memory problem locating (such as memory leakage).

This document describes how to perform memory maintenance and testability on the B2X series, including:

-   Viewing the overall allocation and usage of the system heap memory.
-   Viewing the malloc status of each task (current allocation and peak allocation).
-   Viewing the stack allocation and usage of each task (current usage and peak usage).
-   Viewing where each memory is allocated.

    The memory maintenance and testability commands of AIOT have been integrated into AT commands, and users can directly use these commands.






### Viewing the System Heap Overview<a name="ZH-CN_TOPIC_0000001932358374"></a>

This maintenance and testability function is used to view the heap memory usage of the system.

Command for viewing system heap information: AT+HEAPSTAT

![](figures/zh-cn_image_0000001959437845.png)

### Viewing the Task Stack Usage<a name="ZH-CN_TOPIC_0000001959437769"></a>

This maintenance and testability function is used to view the stack allocation and usage of each task.

You can use this command to optimize and adjust the stack allocation size and save memory.

Command for viewing task stack usage: AT+TASKSTACK

![](figures/zh-cn_image_0000001959517625.png)

### Viewing the Memory Allocation of Each Task<a name="ZH-CN_TOPIC_0000001959517549"></a>

The "task id" here can be obtained through the "AT+HEAPSTAT" or "AT+TASKSTACK" command.

![](figures/zh-cn_image_0000001932199066.png)

### Viewing the Memory Allocation in Interrupts and the Startup Phase<a name="ZH-CN_TOPIC_0000001932198990"></a>

In the system, in addition to the memory allocated in tasks, there is also memory allocated in interrupts and in the system startup phase. These allocations do not belong to any task, so they are classified into a special id.

You can obtain the id corresponding to the non-task alloc through the "AT+HEAPSTAT" command.

The command for viewing the memory allocation in non-task scenarios is also: AT+TASKMALLOC="id", and the display format is the same.

## ADC Common Problem Troubleshooting<a name="ZH-CN_TOPIC_0000001959659845"></a>

1.  Sampling hangs

    There are three common causes of sampling hangs:

    -   The clock or power supply is disabled abnormally: When the ADC is powered on, the required clocks are already enabled. If the required clocks are disabled when entering low power consumption or in other business flows, the calibration sampling and so on may fail. The clocks to be checked include XO\_2\_AFE 0x57008410 bit4 and XO\_2\_ADC 0x57008410 bit1. The power supplies to be checked include NFCLDO 0x5702C230 bit0:3 configured as 0xA, and AFELDO, ADCLDO, and VREFLDO. If the ADC is used for audio sampling, the MICLDO power supply also needs to be enabled and configured as 2.0V.
    -   AMIC and GADC are multiplexed. Because audio sampling and voltage acquisition share the same circuit, time-division multiplexing is required.
    -   ADC sampling does not lock the interrupt. The sampling may hang because it is interrupted by other interrupts.

2.  Abnormal sampling values

    Abnormal sampling values have multiple causes and manifestations. Some typical scenarios and troubleshooting methods are listed as follows:

    -   The error ratio between the sampling value and the actual value is constant, that is, the larger the sampling value, the larger the deviation: Because the ADC range used by BS2X is 0\~1.5V, a voltage divider circuit is often used to divide the voltage to be measured before passing it to the ADC. The accuracy of the divider resistors may introduce errors. Resistors with 1% accuracy are required to reduce the deviation, and the conversion formula must be applied strictly according to the resistor values. Do not use approximate processing. Because floating-point operations are not supported, it is recommended to multiply first and then divide.
    -   The sampling value is low after the first power-on or after waking from sleep: As described above, the voltage divider circuit generally has a capacitor to ground. The measured charging time for a 100nF capacitor to stabilize is about 60ms.
    -   The collected voltage is inaccurate when sampling with the recorded calibration values: Because flashing the recorded calibration values replaces the calibration process, reducing the startup time by about 180ms. During this period, the circuit may not be stable yet. If the recorded calibration values are used, it is recommended to delay 10\~20ms before sampling.

    Troubleshooting methods:

    -   The ADC has a group of critical calibration values, stored in 0x570360D4\~0x570360F4, 9 values in total. Their default values are:

        0x00008000 0x00004000 0x00002000 0x00001000 0x00000800 0x00000800 0x00000400 0x00000200

        Generally, the absolute difference between the calibration result and the default value is within 0x20. A large deviation indicates abnormal calibration. If all values are default values, calibration has not been performed. Calibration values obtained from multiple calibrations may be different, but the difference is extremely small.

    -   The three LDOs of the ADC have their own trim values stored in the efuse. During initialization, they are read and written to the ADC. You can compare whether the values in the two address groups are equal:

        efuse: 0x5702886C\[0-3\], AFELDO\_trim: 0x570363F0\[4-7\]

        efuse: 0x5702886C\[4-7\], ADCLDO\_trim: 0x570363E8\[4-7\]

        efuse: 0x5702886C\[8-11\], VREFLDO\_trim: 0x570363F4\[5-8\]
